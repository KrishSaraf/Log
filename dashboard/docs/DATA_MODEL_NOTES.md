# Data Model Notes — what the spreadsheet says the app should be

Companion to [`SPREADSHEET_ANALYSIS.md`](./SPREADSHEET_ANALYSIS.md). Written against the proposed table
list (`workouts`, `workout_exercises`, `workout_sets`, `health_metrics`, `meals`, `food_entries`,
`questions`, `question_responses`, `insights`) because `dashboard/SCHEMA.md` did not exist at the time of
writing. Where this document and `SCHEMA.md` disagree, `SCHEMA.md` wins.

## The headline

The proposed schema is built for a **workout-and-nutrition app**. The user's two and a half years of
actual behaviour describe a **daily habit tracker with a weight series attached**. Those are different
products, and the mismatch is severe enough to change what gets built first:

- 164 days of logged data, of which **100% have a weight** and **~98% have habit ticks**.
- **0** exercises, **0** sets, **0** reps, **0** logged loads, **0** meals, **0** foods, **0** calories,
  **0** macros, **0** durations, **0** distances, **0** ratings, **0** notes, **0** sleep entries.
- The richest "workout" record in the file is the string `Tenis`.

Five of the nine proposed tables (`workout_exercises`, `workout_sets`, `meals`, `food_entries`,
`insights`) would import **zero rows**. Two tables — `questions` + `question_responses` — would absorb
**1,258 rows**, and `health_metrics` would absorb **164**. That ratio should drive the UI.

## Table-by-table mapping

| Proposed table | Fits? | Rows from this file | Notes |

| `questions` | **Clean fit** | 11 seeded | The habit columns map exactly onto user-defined recurring questions. |
| `question_responses` | **Clean fit** | 1,258 | One per filled habit cell. The core of the import. |
| `workouts` | Partial | 87 | Derivable, but every row is date + type only. No duration, no notes, no detail. |
| `workout_exercises` | **Empty** | 0 | Nothing in the file names an exercise. |

| `meals` | **Empty** | 0 | `Healthy Food` is a yes/half/no tick, not a meal. |

### `health_metrics` — good as specified

`(date, metric, value, unit, source)` is exactly right. Import 164 rows of
`metric = 'body_weight'`, `unit = 'kg'`, `source = 'spreadsheet'`. Value precision is one decimal place
(a single reading, `69.95`, has two), so `numeric(6,2)` is sufficient — do not use an integer type.

One addition worth making: a **unique constraint on `(date, metric, source)`**. The importer needs to be
re-runnable as the user keeps editing the same xlsx, and the natural upsert key is that triple.

### `questions` + `question_responses` — the centre of gravity

This pair is the best-designed part of the proposed schema for this user, and it is where almost all the
data lives. Two things it must get right:

**1. Three-state answers, not booleans.** The user's vocabulary is `✓` / `1/2` / `x`. The `1/2`
("partially done") state is used 21 times, 18 of them on `Healthy Food` — the habit the user is most
ambivalent about. Collapsing it to a boolean throws away the single most behaviourally interesting signal
in the file. Model these as `multiple_choice` with options `yes` / `partial` / `no`, **not** `boolean`.
Store a numeric weight alongside (1.0 / 0.5 / 0.0) so streaks and rolling averages work.

**2. Blank ≠ `x`.** The user writes an explicit `x` when they did not do something, and leaves the cell
blank when they did not open the spreadsheet at all. 161 of 164 logged days carry an explicit `x` or `✓`
for every habit. If `question_responses` has no row for a (question, date) pair, that means *unlogged*,
and the UI must render it as a visual gap rather than a miss. Do not backfill `false`.

### `workouts` — keep it, but expect it to stay thin

87 workout rows are derivable: 40 gym sessions (39 `✓` + 1 `1/2`), 37 sport sessions (30 tennis +
7 cricket, after normalising `Tenis`), 10 generic cardio sessions (8 `✓` + 2 `1/2`). Every one of them is
just a date and a type. If the app demands a duration or an exercise list before a workout can be saved,
**the user will stop logging** — their demonstrated tolerance is one keystroke per habit per day.

Recommendation: make `workouts` creatable from a single tap, with `workout_exercises` / `workout_sets` as
strictly optional progressive disclosure for later. Treat these two tables as forward-looking capacity,
not as import targets.

### Exercise matching against the `exercises` catalogue

Attempted and it comes up empty. The spreadsheet's entire activity vocabulary is `Tennis`, `Tenis`,
`Cricket`. The `exercises` table (876 rows) has no tennis or cricket entry; its 14 `cardio` rows are all
treadmill/trail variants (`Running, Treadmill`, `Trail Running/Walking`, `Walking, Treadmill`). So:

- **Zero rows** should be written to `workout_exercises` from this import.
- The `exercises` table is still valuable as the picker catalogue for future strength logging (`body_part`
  spans 11 groups, `equipment` 11 types), but it cannot be populated from history.
- Consider adding the user's two real sports (`Tennis`, `Cricket`) to the catalogue as `cardio` /
  `body weight` entries, or keeping a separate `activity_type` vocabulary on `workouts`. Right now a
  tennis session has nowhere legitimate to go.

## What is MISSING from the proposed schema

These are things the user demonstrably tracks that the nine tables do not cover.

**1. A first-class habit / streak concept.** Expressing habits as `questions` works mechanically, but the
user's mental model is a **grid**: days down, habits across, ticks in the cells. They have maintained that
grid for months. The app needs a calendar-grid view and per-habit streak/completion stats as a primary
surface, which in turn wants `questions` to carry display metadata — `sort_order`, `icon`, `colour`,
`archived_at` — so the grid can be ordered and styled the way the sheet was.

**2. Question lifecycle / versioning.** The habit set changed three times (June 2024 → July 2024 → the
2026 template). `Multivitamin` was added mid-run and later dropped; `Brush+Braces` became `Brush`;
`Healthy Food` became `Diet`. `questions` therefore needs `active` / `archived_at` and
`effective_from` — otherwise the June 2024 rows look like 30 days of missed multivitamins when the habit
simply did not exist yet. There is no way to represent this in the proposed schema as listed.

**3. Alternative satisfaction of a habit.** `Bath` (5 times) satisfies `Night Clean` by a different
route. The user wants to record *how* they completed something, not just that they did. A nullable
`variant` / `note` string on `question_responses` covers this and also covers `Tennis, Cricket`.

**4. Multiple activities on one day.** `Tennis, Cricket` on 12 Jun 2024 is one cell holding two sessions.
`workouts` must allow multiple rows per date — so no unique constraint on `date` alone.

**5. Explicit "not done" vs "not logged".** Covered above; it needs to be representable, and a
three-state enum plus row-absence does it. Make sure nothing in the schema coerces a missing row to false.

**6. Weight goal / target.** The user lost 8.5 kg over the 2024 run and has regained ~10 kg since. There
is no `goals` table. Even a minimal `goals(metric, target_value, unit, target_date)` would let the
dashboard answer the question the user is obviously asking when they open the app in Sep 2026.

**7. A place for the 2026 template's `Doc Rehab`.** A doctor-prescribed rehab protocol is a recurring
question in form, but it implies an injury context (start date, body part, prescribed frequency) the
schema has nowhere to put. A boolean question is an acceptable v1; note the gap.

## What is UNNECESSARY in the proposed schema

Not "delete these" — they are reasonable forward-looking tables — but **do not build UI for them in v1**,
and do not make them required for anything:

- **`workout_sets`** — the user has never once recorded a set, rep, or load. Any set-logging UI on the
  main path is dead weight and adds friction to the one thing they do reliably.
- **`workout_exercises`** — same; zero historical rows, and no catalogue match for what they actually do.
- **`meals` and `food_entries`** — the user's entire nutrition practice is three ticks a day
  (`Diet`, `Protein`, and formerly `Multivitamin`). A meal-logging flow with per-food macros is an order
  of magnitude more effort than they have ever spent, and there is no evidence they want it. If nutrition
  detail is ever added, it should start as an optional note on the `Diet` response.
- **`workouts.duration` / `distance` / `calories`** (if present) — never recorded; leave nullable and keep
  them off the quick-add form.
- Any **`meal_type` enum** (breakfast/lunch/dinner/snack) — no support in the data at all.

## Units and defaults, from the actual data

| Setting | Value | Evidence |
|---|---|---|
| Body weight unit | **kg** | Header literally reads `Weight (kg)`; all 164 values in 66.5–77.2, unambiguously kg. Never offer lb as default. |
| Weight precision | **1 decimal** | 163 of 164 values have one decimal; store `numeric(6,2)`, display 1 dp. |
| Energy unit | **kcal** | Not in the data. Default kcal (metric-system user, and the global default). |
| Distance unit | **km** | Not in the data; metric user throughout. |
| Load unit (future lifting) | **kg** | Consistent with the one unit they do use. |
| Locale / date display | **`D MMMM (dddd)`, day-first** | Their own format is `22nd October (Tuesday)`. Day-first, weekday always shown. |
| Week start | **Monday** | Not directly evidenced; ISO default, consistent with a day-first metric user. |
| Timezone / granularity | **date only, no time** | Nothing in the file has a time component. Use `date`, not `timestamptz`, for daily logs. |

### Note on the `m` question

`M` is a single-letter column with no expansion anywhere in the workbook. It has the highest completion
rate of any habit (57.1%, 92 of 161 days) so it clearly matters to the user. Seed it with the literal key
and prompt `M`, flag it `private` in config so it can be blurred/hidden in shared views, and surface a
rename affordance on first run. Guessing at its meaning in the UI would be both wrong and intrusive.

## Recurring personal questions the user does NOT track

Worth stating plainly so the product does not invent them: there is **no** mood scale, **no** energy
rating, **no** sleep duration or quality, **no** productivity metric, **no** stress, **no** soreness,
**no** water intake, **no** step count, and **no** free-text journal anywhere in 595 rows. Every rating
scale in the app will be a new behaviour, not a migration. Ship 1–2 such questions at most (energy or
sleep are the natural first asks given the weight regain), make them optional, and let the proven habit
grid carry the daily-open habit.

## Import-behaviour recommendations

1. **Normalise `Tenis` → `Tennis`** on the way in (25 of 30 tennis records are misspelled).
2. **Key on header text, never column index** — positions differ across the three eras.
3. **Resolve the year from the sheet name**, with the weekday text as a validation check; log the one
   known mismatch (`10th July (Wedesday)`) rather than failing on it.
4. **Skip the 13 empty template sheets** but do not delete them conceptually — the 2026 headers are the
   spec for the current question set.
5. **Treat `1`/`0` as `✓`/`x`** (only affects 1–4 Jul 2024 plus a few `June` cells).
6. **Route the stray `Tenis` in the `Gym` column** (21 Nov 2024) to a tennis workout, not a gym one.
7. **Make the import idempotent** via natural keys — the user is still editing this file (last touched
   2026-09-19), so re-import must not duplicate.
